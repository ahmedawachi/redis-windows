    How the Windows CI numbers are produced

    Benchmarks run with ci/bench.sh in the Verify workflow. Each toolchain gets one windows-latest runner; the stock and fork packages are benchmarked on it one repetition at a time, interleaved, three times over, and the page shows the median of the repetitions. BGSAVE runs several saves per repetition, so its figures are the median of every save.

    for rep in 1 2 3; do
  BENCH_LABEL=baseline BENCH_REPS=1 BENCH_REP_START=$rep bash ci/bench.sh "packages/$base" "$csv"
  BENCH_LABEL=fork BENCH_REPS=1 BENCH_REP_START=$rep bash ci/bench.sh "packages/$fork" "$csv"
done
bash ci/bench.sh --compare "$csv" baseline fork

    Sizes used by the Windows job: BENCH_N_SMALL=20000, BENCH_N_PIPE=200000, BENCH_N_LARGE=300, BENCH_POPULATE_MB="64 256", BENCH_BGSAVE_REPS=3.

    • small: SET, GET, HSET of 3-byte values at -P1 -c1 and at -P16 -c50.
    • large: SET and GET of a ~1.9 MB value at -c4.
    • hmget: HMGET key absexp sldexp data with a ~1.9 MB data field, at -c1 and -c2: the IDistributedCache read shape that failed in production.
    • hset: HSET key absexp sldexp data with a ~1.9 MB data field.
    • bgsave: DEBUG POPULATE to each dataset size, then repeated BGSAVEs: fork time (the main-thread stall), BGSAVE wall time and child CPU.

    Metrics come from redis-benchmark (throughput, average, p50, p99 and max latency) and from the server's own INFO cpu: server CPU is user + sys, and CPU per operation is (user + sys) divided by the number of requests. User CPU is never reported alone.

    Caveats

    • Both builds run on the same runner, interleaved, so they see the same machine. Differences under about 10% are within runner noise; bars and tiles inside that band are shown as neutral.
    • A proxy measurement on a non-Windows host is not a Windows measurement. Proxy datasets are badged on every chart; Windows numbers come from the benchmark job.
